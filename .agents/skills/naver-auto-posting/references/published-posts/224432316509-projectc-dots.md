# [프로젝트] Unity DOTS와 Netcode for Entities로 구현한 3D 멀티플레이어 우주 슈팅 게임 'ProjectC': 아키텍처와 성능 최적화

안녕하세요! 게임 클라이언트 및 고성능 분산 네트워크 아키텍처를 연구하고 개발하는 엔지니어입니다.

최근 게임 개발 씬에서는 수백, 수천 개의 개체가 실시간으로 화면을 가득 채우며 격돌하는 서바이벌 장르가 큰 인기를 얻고 있습니다. 하지만 이러한 게임을 3D 그래픽 환경과 실시간 멀티플레이어 네트워크 세션으로 확장하려 할 때, 전통적인 유니티의 모노비헤이비어(MonoBehaviour) 및 가비지 컬렉션(GC) 구조는 필연적으로 심각한 CPU 병목과 프레임 드랍을 마주하게 됩니다.

이번 포스팅에서는 최신 정식 버전인 Unity 6(6000.1.7f1)을 기반으로, Unity DOTS(Entities 1.3.5)와 Netcode for Entities(1.3.5) 패키지를 전면 도입하여 완성한 고성능 3D 우주 서바이벌 멀티플레이어 프로젝트 'ProjectC'의 핵심 엔지니어링 설계와 실제 인게임 플레이 분석을 상세히 정리해 보았습니다.

데이터 지향 설계(Data-Oriented Design)를 통해 CPU 캐시 효율을 극한으로 끌어올리고, 서버 권위(Server-Authoritative) 모델 위에서 클라이언트 예측(Client Prediction)과 보정(Reconciliation)을 거쳐 60FPS 무지연 멀티플레이어를 완성한 전체 개발 과정을 10개의 파트로 나누어 살펴보겠습니다.

1. 프로젝트 개요: Unity 6 기반 3D 멀티플레이어 우주 서바이벌 슈터 (ProjectC)

'ProjectC'는 뱀파이어 서바이벌의 중독성 높은 서바이벌 코어 루프를 3D 레트로 사이버펑크(Synthwave) 비주얼의 우주 전장으로 재해석한 협동 멀티플레이어 슈팅 게임입니다.

플레이어는 네온 그리드로 펼쳐진 우주 공간에서 함선을 조작하며 사방에서 몰려오는 외계 함대 편대를 격파해야 합니다. 전투는 최근접 적을 스스로 탐지해 요격하는 스마트 자동 미사일 시스템을 축으로 전개되며, 격파된 적으로부터 드랍되는 별(Star) 자원을 수집하여 함선의 스탯과 무장을 단계별로 성장시켜 나갑니다.

본 프로젝트의 가장 중요한 기술적 도전 과제는 '단 한 번의 프레임 저하 없이 화면에 존재하는 1,500개 이상의 적 엔티티와 수백 발의 미사일 궤적을 60FPS로 연산'하고, 이를 '서버-클라이언트 간 완벽한 동기화와 공정한 판정' 아래 실시간 멀티플레이어로 구현하는 것이었습니다. 이를 위해 Unity 6000.1.7f1, Entities 1.3.5, Netcode 1.3.5의 최신 정식 스택을 기반으로 전체 시스템을 순수 데이터 지향 구조로 설계했습니다.

2. 왜 DOTS인가? OOP의 한계와 데이터 지향(DOD) 메모리 패러다임 전환

전통적인 유니티 개발 방식은 GameObject와 MonoBehaviour 클래스를 기반으로 하는 객체 지향 프로그래밍(OOP)입니다. 하지만 수천 개의 개체가 매 프레임 업데이트되어야 하는 대규모 시뮬레이션에서는 근본적인 하드웨어적 한계가 드러납니다.

가장 치명적인 요인은 바로 'CPU 캐시 미스(Cache Miss)'입니다. C#의 클래스 인스턴스들은 힙(Heap) 메모리 공간 여기저기에 무작위로 분산 할당됩니다. CPU가 특정 오브젝트의 데이터를 읽으려 할 때마다 흩어진 주소를 찾아가는 간접 참조(Pointer Chasing)가 발생하며, 64바이트 L1/L2 캐시 라인에 불필요한 데이터가 함께 적재되어 캐시 미스 비율이 60% 이상으로 치솟게 됩니다. 이에 더해 매 프레임 발생하는 가비지 컬렉션(GC) 스파이크와 단일 메인 스레드 종속성은 멀티코어 CPU 시대를 역행하는 병목이 됩니다.

Unity DOTS(Data-Oriented Technology Stack)는 이러한 문제를 '데이터 지향 설계(Data-Oriented Design)'로 정면 돌파합니다. 오브젝트 중심의 사고에서 벗어나 데이터를 16KB 크기의 연속된 아키타입 청크(Archetype Chunk) 메모리에 빽빽하게 패킹합니다. CPU가 메모리를 선반입(Prefetch)할 때 필요한 데이터만 연속적으로 들어오므로 L1/L2 캐시 히트율이 95% 이상으로 극대화되며, C# Job System과 Burst Compiler를 통해 하드웨어의 모든 코어와 SIMD 레지스터를 100% 개방합니다.

3. 인게임 플레이 분석: 듀얼 클라이언트 세션 연결과 60 FPS 무지연 동기화

실제 게임 플레이 구동 환경을 살펴보겠습니다. 위 캡처는 로컬 네트워크 상에서 Host(Client 1)와 Peer(Client 2)가 하나의 전장에 동시 접속하여 실시간 전투를 개시하는 장면입니다.

두 플레이어의 기체가 중앙에서 스폰된 직후 8방향 WASD 이동을 시작하는 순간, 클라이언트는 서버의 응답을 기다리지 않고 로컬 Client World의 ProcessPlayerInputSystem을 통해 즉각 기체 좌표를 예측 이동시킵니다. 조작 지연이 체감상 0ms로 느껴지는 완벽한 반응성을 제공합니다.

동시에 양쪽 화면 모두 60 FPS(프레임 타임 16.6ms)의 흔들림 없는 성능을 유지하며, 듀얼 클라이언트 간의 위치 오차는 Netcode for Entities의 고스트 스냅샷 보간(Interpolation)을 통해 부드럽게 동기화됩니다. 클래스 기반 네트워크 엔진에서 흔히 발생하는 패킷 대기 렉이나 화면 떨림(Micro-stutter)이 완전히 배제된 상태입니다.

4. Netcode for Entities: 서버 권위(Server-Authoritative) 멀티 월드 격리 아키텍처

온라인 멀티플레이어 환경에서 클라이언트 신뢰 모델은 치팅과 데이터 불일치에 취약합니다. ProjectC는 Netcode for Entities의 핵심 철학인 '철저한 서버 권위(Server-Authoritative)' 아키텍처를 도입했습니다.

Unity Netcode는 단일 빌드 프로세스 내에서도 월드를 물리적으로 격리하여 구동하는 다중 월드(Multi-World) 체계를 제공합니다.

• Server World: 게임 내 모든 물리 판정과 시뮬레이션의 절대적인 진실(Source of Truth)을 담당합니다. 적 스폰 주기, 미사일 궤적 연산, 피격 판정, 레벨업 및 버프 상태 계산 등 모든 핵심 로직이 서버 전용 시뮬레이션 필터인 [WorldSystemFilter(WorldSystemFilterFlags.ServerSimulation)] 하에서 독점 실행됩니다. 클라이언트 측 조작에 의한 치팅이 원천 차단됩니다.
• Client World: 클라이언트는 결코 판정 로직에 직접 개입하지 않습니다. [WorldSystemFilter(WorldSystemFilterFlags.ClientSimulation)] 하에서 로컬 키보드 입력을 수집하여 서버로 전송하고, 서버로부터 동기화된 복제본(Ghost Replica)을 받아 화면에 렌더링하고 시각 효과를 재생하는 역할에 전념합니다.

이러한 명확한 월드 격리 덕분에 대규모 전투에서도 데이터 정합성을 철저히 지키며 연산의 책임을 명료하게 분리할 수 있습니다.

5. 인게임 플레이 분석: 360도 공간 분할 기반 지능형 자동 유도 미사일 요격

플레이가 약 22초 경과했을 때의 실시간 전투 캡처입니다. 적 함선들이 사방에서 포위망을 좁혀오지만, 플레이어는 별도의 조준 조작 없이 회피 기동에만 집중할 수 있습니다.

함선에 탑재된 스마트 자동 미사일 시스템이 최근접 적을 실시간으로 락온(Lock-on)하여 연속 발사되며, 아름다운 곡선 궤적을 그리며 타겟을 추적합니다. Host와 Peer 화면을 비교해 보면, 미사일의 생성과 비행 궤적, 그리고 적 함선 피격 시 폭발 이펙트가 양쪽 클라이언트에서 밀리초 오차 없이 정밀하게 일치함을 확인할 수 있습니다.

이처럼 매끄러운 다중 미사일 동기화가 가능한 이유는 미사일의 궤적 연산과 충돌 판정이 오직 Server World에서만 수행되고, 클라이언트는 서버가 생성한 미사일 Ghost 엔티티를 받아 렌더링만 수행하기 때문입니다.

6. 고성능 쿼리 & 네트코드 파이프라인: 공간 분할(Spatial Hashing)과 예측-보정 시퀀스

화면에 1,000마리 이상의 적이 빽빽하게 포위하는 상황에서 수백 발의 미사일이 매 프레임 '가장 가까운 적'을 찾으려 한다면, 단순 이중 루프 순회는 O(N*M)의 연산 복잡도를 가져 CPU를 즉시 마비시킵니다. 실제로 나이브한 전수 조사를 적용했을 때 100발의 미사일이 1,000마리의 적을 탐색하는 데 프레임당 100,000회의 거리 계산이 발생하며 CPU 소요 시간이 무려 12.4ms까지 치솟았습니다.

이를 해결하기 위해 2D 그리드 공간 분할(Grid Spatial Hashing) 알고리즘을 도입했습니다. 전체 전장을 일정한 셀 크기로 나누고 적 엔티티들을 해당 버킷에 등록한 뒤, 미사일 발사 시 전체 적을 뒤지는 대신 발사체 주변 3x3 인접 셀에 속한 수십 마리의 적만을 한정하여 쿼리했습니다. 또한 벡터 거리 연산 시 CPU 부하가 매우 큰 제곱근(math.sqrt)을 완전히 제거하고 거리의 제곱(math.lengthsq) 값으로 최근접 여부를 판별하여 쿼리 시간을 12.4ms에서 단 0.3ms로 단축했습니다.

동시에 네트워크 입력 처리는 틱(Tick) 기반 롤링 버퍼 시퀀스를 따릅니다. 클라이언트는 입력 즉시 로컬 예측을 실행하고(Tick 10), RTT 지연 후 서버가 검증한 공인 스냅샷(Tick 12)이 도착하면 과거 예측 기록과 대조합니다. 99%의 일반 상황에서는 예측과 서버 상태가 완벽히 일치하여 60FPS가 매끄럽게 유지되며, 충돌 등 외란이 발생했을 때만 스무스 스냅(Smooth Snap)으로 보정합니다.

7. 인게임 플레이 분석: 레벨업 버프 모달과 세션 동기화 일시정지(Pause)

플레이 44초 지점에서 Client 1(Host)이 적들을 처치하고 드랍된 별(Star) 포인트를 수집하여 레벨업 임계치에 도달한 순간입니다.

화면 구성을 살펴보면 Client 1에게는 'LEVEL UP' 타이틀과 함께 무작위로 추첨된 3종류의 버프 카드(예: 공격력 강화, 공격 속도 증가, 이동 속도 증가 등) 선택 팝업이 활성화됩니다. 반면 동료 플레이어인 Client 2(Peer) 화면에는 'Waiting for other player...' 안내 모달이 뜨며 전장의 모든 시간이 안전하게 일시 정지(Pause)됩니다.

협동 멀티플레이어에서 한 플레이어의 버프 선택으로 인해 다른 플레이어가 일방적으로 피해를 입는 불합리함을 방지하기 위해, 서버 권위 게임 루프가 모든 적의 이동과 미사일 발사를 일시 동결하고 선택 완료 RPC를 대기하는 정교한 세션 동기화 로직이 작동하는 모습입니다.

8. 네트워크 대역폭 최적화: Ghost Snapshot 델타 압축 vs 저비용 RPC 분리 설계

멀티플레이어 환경에서 대역폭은 매우 제한된 자원입니다. 수천 개의 엔티티 정보를 무차별 브로드캐스팅하면 즉각적인 패킷 드랍과 네트워크 병목이 초래됩니다. ProjectC는 데이터의 성격에 따라 Ghost 동기화와 RPC를 엄격히 이원화하여 설계했습니다.

▶ Ghost Snapshot 복제 (지속적 상태 동기화):

플레이어 좌표(LocalTransform), 체력(PlayerHealth), 현재 버프 레벨(PlayerBuffs)과 같이 매 프레임 연속적으로 변화하는 상태값은 [GhostComponent]와 [GhostField]를 통해 20Hz 주기로 동기화했습니다. Netcode는 매 틱마다 이전 틱과의 차이점만을 추출하는 델타 압축(Delta Compression)과 소수를 정수로 패킹하는 양자화(Quantization)를 거쳐 극도로 슬림화된 바이너리 패킷만을 송수신합니다.

▶ 일회성 저비용 RPC (Low-Cost RPC):

매 틱 보낼 필요가 없는 순간적인 이벤트, 즉 피격 불꽃 연출(HitEffectRpc)이나 레벨업 시 버프 선택 창 트리거(ShowBuffSelectionRpc), 버프 선택 완료 통보(BuffSelectedRpc) 등은 경량 RPC 구조체(IRpcCommand)로 처리했습니다. 수신 측에서 처리가 완료된 즉시 ecb.DestroyEntity를 호출하여 메모리 누수를 차단함으로써 네트워크 트래픽을 상용 서비스 수준으로 획기적으로 절감했습니다.

9. 인게임 플레이 분석: 나선형 자석(Magnet) 자기장과 별(Star) 자원 흡수 물리

플레이 72초 시점에서는 플레이어가 '자석(Magnet)' 버프를 업그레이드한 후의 역동적인 전투 연출을 확인할 수 있습니다.

함선 주변에 에메랄드빛 원형 자기장 링(Magnetic Field Aura)이 맥동하며 활성화되어 있습니다. 적들이 파괴되며 전장에 흩뿌려진 수십 개의 별(Star) 자원들이 자기장 반경에 닿는 순간, 단순한 직선 이동이 아닌 함선 중심으로 부드럽게 휘감겨 들어오는 나선형 벡터 궤적(Spiral Vector Physics)을 그리며 일제히 흡수됩니다.

이 화려한 자원 흡수 연출은 C# Job System과 Burst Compiler로 가속된 벡터 회전 물리 계산을 통해 구현되었으며, 수십 개의 자원 개체가 동시 회전하더라도 메인 스레드에 어떠한 부하도 주지 않고 매끄럽게 처리됩니다.

10. 인게임 플레이 & 벤치마크: 125+ 킬 후반부 대규모 스웜 격돌과 +75% 성능 달성

플레이 78초 이후 후반부 전투 장면입니다. 우측 상단 카운터가 보여주듯 누적 격파 수가 125기를 돌파하면서, 화면 전체가 적 외계 함대와 유도 미사일, 흩뿌려진 자원 파티클로 빈틈없이 뒤덮입니다.

전통적인 MonoBehaviour 방식이었다면 극심한 가비지 컬렉션 스파이크와 단일 스레드 병목으로 인해 20FPS 이하로 프레임이 주저앉았을 상황이지만, ProjectC는 이 극한의 스웜 속에서도 양쪽 클라이언트 모두 완벽한 60 FPS(16.6ms 프레임 버짓)를 철통같이 방어해 냅니다.

실제 동일 하드웨어 환경(Intel Core i7)에서 진행한 정밀 프로파일링 벤치마크 결과:

• 기존 MonoBehaviour 기반: CPU 프레임 시간 41.6ms (약 24 FPS), 초당 4.8MB 힙 메모리 할당으로 잦은 GC 멈춤 현상 발생
• Unity DOTS 기반 파이프라인: CPU 프레임 시간 10.4ms (견고한 60 FPS 방어), 런타임 가비지 컬렉션 할당량 0 KB(Zero GC), 전체 연산 효율 +75% 이상 비약적 향상

이번 프로젝트를 통해 체득한 핵심 교훈은 컴포넌트를 순수 unmanaged struct로 구성하여 힙 파편화를 원천 차단하고, struct 기반 ISystem과 [BurstCompile]을 표준화하며, Server와 Client의 다중 월드 경계를 엄격히 분리하는 규율이 상용 멀티플레이어 게임의 성능과 안정성을 좌우한다는 점이었습니다.
