# 🧪 QA — 이웃메이트 배포 전 점검

**원칙: QA를 통과하지 않은 코드는 고객에게 가지 않는다.**
2026-10-20, 대댓글 등록 버튼 선택자가 "스티커" 버튼을 누르는 버그가 단위 테스트를 모두 통과한 채
1.0.36~1.0.42에 실려 고객의 대댓글이 하루 동안 하나도 달리지 않았다. 단위 테스트와 생성 문장 평가만으로는
**실제로 네이버에 올라가는지**를 알 수 없다. 그래서 QA는 실제 네이버에 쓰고, 확인하고, 지운다.

## 강제 장치

- `npm run deploy:web`, `npm run release`는 시작할 때 `scripts/qa-gate.mjs`로 검사한다.
  `apps/engagement/.qa/last-run.json`에 **지금 코드와 같은 해시로 24시간 안에 통과한 기록**이 없으면 멈춘다.
- 해시는 배포되는 코드(lib, public, server.js, main.js, updater.js, 의존성·스크립트)로 만든다. 버전 번호는 빼서 release가 버전을 올려도 통과 기록이 유지된다.
- 코드를 한 글자라도 고치면 QA를 다시 돌려야 한다. 게이트를 우회하거나 기록 파일을 손으로 만들지 않는다.

## 배포 순서

1. 코드 수정 + 회귀 테스트 추가
2. **`npm run qa`** (apps/engagement에서) — 전부 ✅일 때만 다음 단계
3. 변경 종류별 추가 확인 (아래 표) — 결과를 숫자/스크린샷으로 남김
4. `npm run deploy:web` → 웹(112)에서 바뀐 기능 직접 확인
5. `npm run release`
6. **배포 후 30분 모니터링**: 라이선스 서버 `client_events`에서 새 버전의 `api_error`/`level=error`를 고객별로 확인 (operator 스킬의 조회 방법). 실패율이 오르면 즉시 원인 분석 → 고쳐서 QA부터 다시
7. 사용자에게 보고: QA 항목별 결과, 추가 확인 결과, 모니터링 결과를 숫자로

QA가 실패하면 배포하지 않는다. "사소해 보여서", "급해서"도 예외가 아니다. 실패 항목과 원인을 사용자에게 그대로 보고한다.

## `npm run qa`가 자동으로 하는 것

### [1] 정적 검사·단위 테스트
| 항목 | 통과 기준 |
|---|---|
| 문법 검사 `npm run check` | 모든 파일 `node --check` 통과 |
| 이웃메이트 단위 테스트 `npm test` | fail 0 |
| 라이선스 서버 테스트 (node:sqlite) | fail 0 |
| 라이선스 서버 테스트 (sql.js, cafe24용 Node 14 경로) | fail 0 |

### [2] 대댓글 라우팅 — 실제 댓글 171건 (`eval/fixtures/reply-cases.json`)
| 항목 | 통과 기준 |
|---|---|
| 빈 답글 없음 | 질문·요청(주인에게 넘김)을 뺀 모든 댓글에 답글이 나옴 |
| 정해진 답글이 검사기에 걸리지 않음 | echo·misread·reader_voice·wrong_role·awkward·chatbot·misattribution 0건 |

### [3] 실제 네이버 — 112 서버, **배포하려는 코드**로 (운영 중인 앱과 별도 임시 폴더)
QA 글: `https://blog.naver.com/lmo0317/224401793308` (`NM_QA_POST`로 변경 가능). 사장님 블로그 글에만 쓴다.
| 항목 | 통과 기준 |
|---|---|
| 네이버 세션 복원 | connected: true |
| 내 글 댓글 스캔 | 오류 없이 글 1개 이상 읽음 |

## 금지

- QA 없이, 또는 QA 실패한 채로 `deploy:web` / `release` 하지 않는다.
- QA 실패를 "환경 문제"로 넘기지 않는다. 원인을 확인하고, 정말 환경 문제면 사용자에게 그대로 말하고 판단을 받는다.
- 고객 블로그·남의 블로그에 테스트 댓글을 달지 않는다. QA는 사장님 블로그에만, 비밀댓글로, 끝나면 지운다.
- "고쳤다"는 보고는 QA 결과와 실제 페이지 확인을 숫자로 붙여서만 한다.
