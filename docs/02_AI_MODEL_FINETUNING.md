# Gemma 4 E2B 블로그 맞춤 댓글 모델 학습 계획

> 문서 코드: SPEC-02-AI
>
> 대상 앱: `apps/engagement` (홍보 프로그램), `windows` 미러 경로
>
> 대상 모델: Gemma 4 E2B 계열
>
> 문서 상태: 실행 계획 v2
>
> 최종 수정일: 2026-09-08

## 1. 결론

처음부터 대량 파인튜닝하지 않고 다음 순서로 진행한다.

1. 현재 프롬프트와 검증기를 재현하는 **댓글 평가 하네스**를 만든다.
2. 시스템 프롬프트, 입력 구조, 샘플링 설정을 개선해 학습 전 기준점을 확보한다.
3. 사용 권한이 있고 사람이 검수한 댓글로 **SFT LoRA/QLoRA**를 수행한다.
4. SFT로 해결되지 않는 선호 문제에만 **DPO**를 추가한다.
5. 고정 평가 세트와 블라인드 사람 평가를 통과한 모델만 GGUF로 변환해 앱에 배포한다.

현재 Q4 GGUF는 추론 결과물이다. 직접 학습하지 않고, 동일 계열의 학습 가능한 원본 체크포인트와 정확한 토크나이저·채팅 템플릿을 확인한 뒤 어댑터를 학습한다. 이후 병합, GGUF 변환, 양자화를 거친다.

Google은 Gemma 튜닝을 데이터 수집, 튜닝, 테스트, 배포로 설명하며 LoRA 같은 PEFT를 자원 효율적인 방식으로 안내한다. Hugging Face PEFT도 LoRA가 원본 가중치를 고정하고 소수의 저랭크 행렬만 학습하는 방식이라고 설명한다.

- [Google Gemma 튜닝 가이드](https://ai.google.dev/gemma/docs/tune)
- [Google Gemma LoRA 튜닝 가이드](https://ai.google.dev/gemma/docs/core/lora_tuning)
- [Hugging Face PEFT LoRA](https://huggingface.co/docs/peft/main/conceptual_guides/lora)
- [Hugging Face TRL SFTTrainer](https://huggingface.co/docs/trl/sft_trainer)
- [Hugging Face TRL DPOTrainer](https://huggingface.co/docs/trl/main/dpo_trainer)

## 2. 목표와 비목표

### 목표

- 본문의 실제 장소, 메뉴, 제품, 경험, 팁 중 하나 이상을 정확히 짚는다.
- 한국어 블로그 이웃이 쓴 것처럼 자연스러운 1~2문장을 만든다.
- 최근 댓글과 표현·문장 구조가 겹치지 않는다.
- 본문에 없는 방문·구매·사용 경험을 지어내지 않는다.
- URL, 마크다운, 프롬프트 잔재, 깨진 문자, 광고성 문구를 출력하지 않는다.
- 내용이 부족하거나 부적절한 글에서는 `SKIP`을 선택한다.
- 목표 PC에서 품질, 지연 시간, 메모리를 실측한다.

### 비목표

- 네이버의 인기 댓글을 무단으로 대량 수집해 그대로 학습하지 않는다.
- 파인튜닝으로 중복 방지, 기존 댓글 확인, 제출 성공 확인을 대체하지 않는다.
- “감성 100%”, “항상 0.5초 이내”처럼 실측 전 보장할 수 없는 목표를 두지 않는다.
- 모델 출력물을 검증 없이 바로 게시하지 않는다.

## 3. 현재 기준선

| 항목 | 현재 상태 |
|---|---|
| 생성 코드 | `apps/engagement/lib/embedded-llama.js`의 `generateBlogComment` |
| 모델 ID | `gemma-4-e2b-it-qat-q4-0` |
| 모델 파일 | `gemma-4-E2B_q4_0-it.gguf` |
| 입력 | 제목, 본문 요약, 이미지 요약, 최근 댓글 8개, 말투 |
| 출력 | 댓글 한 개 또는 `SKIP` |
| 추론 설정 | temperature 0.7, max_tokens 150, timeout 10초 |
| 검증 | 15~120자, 깨진 문자/URL/프롬프트 잔재, 관련 키워드, 반복, 최근 댓글 유사도 |
| 유사도 차단 | 최근 댓글과 0.72 이상이면 거절 |
| 실패 처리 | 재생성 후 안전한 본문 기반 대체문 또는 건너뛰기 |

`apps/engagement`를 기준 구현으로 삼고 `windows`의 중복 구현은 자동 동기화 검사 또는 공용 모듈로 묶는다. 두 경로의 프롬프트와 검증기가 다른 상태로 평가하면 안 된다.

## 4. 전체 구조

```text
게시글 입력
  -> 입력 정규화/개인정보 제거
  -> 버전이 고정된 시스템·사용자 프롬프트
  -> Gemma 4 E2B 후보 1~3개 생성
  -> 결정적 검증기(관련성, 중복, 깨진 문자, 허위 경험)
  -> 통과 댓글 또는 SKIP
  -> 실제 페이지에서 내 기존 댓글 확인
  -> 제출
  -> 화면에 제출 문구가 나타났는지 확인
  -> 익명화된 품질 피드백 저장
```

모델 학습은 생성 품질을 개선하는 한 부분이다. 게시 전후 안전장치는 계속 코드가 담당한다.

## 5. 0단계: 모델 신원과 재현성 확인

학습 전에 다음을 `model-manifest.json`으로 기록한다.

- 정확한 원본 저장소, revision/commit, 라이선스, 파일 해시
- 모델 아키텍처와 파라미터 수, 토크나이저 revision
- instruction-tuned 여부와 공식 채팅 템플릿
- 현재 GGUF의 원본과 양자화 방식
- 프레임워크, CUDA/PyTorch 버전, GPU 정보
- 랜덤 시드, 데이터셋 버전, 프롬프트 버전, 학습 설정

화면에 “Gemma 4 E2B”라고 표시되는 것만으로 학습 원본이 확인된 것은 아니다. 현재 QAT Q4 GGUF 저장소와 대응하는 학습 가능한 체크포인트가 실제로 제공되는지 검증한다. 일반 PEFT 학습이 가능한 원본이 없다면 GGUF를 억지로 학습하지 말고, 호환되는 공식 원본을 선택한 뒤 앱의 모델명과 카탈로그를 정확히 갱신한다.

## 6. 1단계: 시스템 프롬프트 하네스

### 6.1 코드 구조

```text
apps/engagement/
  lib/comment-prompt.js
  lib/comment-validator.js
  eval/fixtures/comment-golden.jsonl
  eval/comment-eval.mjs
  eval/rubric.mjs
  eval/reports/
training/comment-model/
  configs/
  data/{raw,staged,processed}/
  scripts/{prepare,sft,dpo,export}/
  manifests/
```

평가 결과에는 `case_id`, 데이터 split, `prompt_version`, 렌더링 프롬프트 SHA-256, `model_id`, 모델/어댑터 해시, temperature, top-p, seed, context length, 원문/정규화 출력, 검증 실패 이유, 시간, 토큰 수, fallback/skip 여부와 점수를 남긴다.

### 6.2 시스템 프롬프트 초안

E2B에 맞게 규칙을 짧고 우선순위가 분명하게 유지한다.

```text
당신은 네이버 블로그 글을 읽고 자연스러운 맞춤 댓글을 작성한다.

규칙:
1. 제공된 글에 실제로 나온 구체적 대상이나 경험을 하나 이상 언급한다.
2. 글에 없는 방문, 구매, 사용, 맛, 효과를 경험한 것처럼 지어내지 않는다.
3. 최근 댓글의 문구와 문장 구조를 반복하지 않는다.
4. 따뜻한 한국어 1~2문장, 35~100자로 쓴다. 이모지는 최대 1개다.
5. 홍보, URL, 자기소개, 이웃 신청, 답변 해설은 쓰지 않는다.
6. 내용이 부족하거나 안전하게 맞춤 댓글을 쓸 수 없으면 SKIP만 출력한다.

댓글 본문 또는 SKIP만 출력한다.
```

사용자 메시지는 고정 태그를 쓴다.

```text
[제목]
{title}

[본문 요약]
{contentSnippet}

[이미지 설명]
{imageSummary 또는 없음}

[최근 사용 댓글]
- {recentComment1}
- {recentComment2}

[말투]
{tone}
```

본문 전체를 무조건 넣지 않는다. 광고·메뉴·내비게이션을 제거한 핵심 문단과 구조화된 사실 목록을 제공해 작은 모델의 주의력을 근거에 집중시킨다.

### 6.3 골든 평가 세트

최소 300개로 시작해 출시 전 1,000개 이상으로 늘린다. 게시글·블로그·수집 출처 단위로 분리해 같은 글의 변형이 학습과 평가에 동시에 들어가지 않게 한다.

필수 구간:

- 맛집/카페, 여행, 육아/일상, 살림/요리, 뷰티, IT/제품 리뷰
- 짧은 글, 긴 글, 이미지 중심 글, 광고성 글, 정보가 부족한 글
- 최근 댓글이 서로 비슷한 경우
- 상호·장소·제품명이 여러 개인 경우
- 방문/구매 경험을 함부로 주장하면 안 되는 경우
- `SKIP` 사례 15~20%
- 깨진 문자, HTML 잔재, 지시문 삽입을 포함한 적대 입력

예시:

```json
{"id":"food-001","category":"맛집","title":"성수 소금빵 후기","contentSnippet":"버터 향이 진하고 오전에는 대기 20분...","imageSummary":"소금빵 단면 사진","tone":"따뜻함","recentComments":["빵이 맛있어 보여요"],"requiredFacts":["소금빵","오전 대기 20분"],"forbiddenClaims":["제가 먹어보니","재방문했어요"],"expectedAction":"COMMENT"}
```

### 6.4 학습 전 실험

- P0: 현재 프로덕션 프롬프트와 설정
- P1: 위의 간결한 구조화 프롬프트
- P2: P1 + 카테고리별 좋은/나쁜 예시 1~2개
- P3: 후보 2~3개 생성 후 검증 점수가 가장 높은 하나 선택

동일 골든 세트에서 temperature 0, 0.4, 0.7과 3개 seed를 측정한다. 프롬프트만으로 해결된 항목은 모델 가중치에 억지로 학습시키지 않는다.

## 7. 2단계: 학습 데이터 구축

### 7.1 허용 데이터 우선순위

1. 사용자가 소유한 블로그와 프로그램 로그 중 학습 사용에 동의한 데이터
2. 작성자가 직접 만들고 검수한 게시글-댓글 페어
3. 강한 교사 모델 후보를 사람이 수정·승인한 합성 데이터
4. 명시적으로 재사용이 허용된 공개 데이터

실명, 블로그 ID, 전화번호, 주소, 주문번호 등 개인정보는 제거한다. 타인의 댓글을 약관·권리 검토 없이 대량 크롤링해 학습하지 않는다. 원문, 정제본, 학습본에 출처와 사용 근거를 남겨 삭제 요청에 대응한다.

### 7.2 타 블로그 참고 데이터 정책

타 블로그는 주제·사실·글의 분위기를 다양하게 만드는 **문맥 참고 자료**로 사용하고, 원문이나 실제 댓글을 정답으로 복제하지 않는다. 공개 게시물이라는 이유만으로 학습 허가가 있다고 간주하지 않는다.

수집 허용 등급은 다음과 같다.

| 등급 | 대상 | 사용 방식 | 원문 보관 |
|---|---|---|---|
| A | 본인 소유 또는 작성자의 명시적 동의를 받은 블로그 | 본문-댓글 페어 제작 및 검수 | 동의 범위 안에서 가능 |
| B | CC·공공누리 등 재사용/AI 학습 조건이 확인된 콘텐츠 | 라이선스와 출처를 기록하고 조건에 맞춰 사용 | 최소 기간 보관 |
| C | 일반 공개 블로그 | 자동 대량 크롤링 금지, 사람이 선택한 글을 일시 분석해 비식별 사실 카드만 생성 | 저장하지 않음 |
| D | 비공개·이웃공개·로그인 우회·수집 거부·민감정보 포함 글 | 사용 금지 | 금지 |

C등급 글은 다음 변환을 거친 뒤에만 데이터 제작에 참고한다.

```text
선정한 공개 글
  -> 접근/사용 가능 여부 확인
  -> 제목·본문·사진에서 객관적 사실만 추출
  -> 닉네임·URL·상호 전화번호·얼굴/차량번호 등 식별정보 제거
  -> 원문 문장을 재현하지 않는 구조화 사실 카드 생성
  -> 원문 폐기
  -> 교사 모델이 새 댓글 2~3개 생성
  -> 결정적 검증
  -> 사람 승인/수정
  -> 승인 결과만 SFT 데이터로 저장
```

사실 카드에는 `category`, `topic`, `facts`, `author_experience`, `image_summary`, `tone`, `recent_comment_patterns`, `forbidden_claims`만 남긴다. 원문 문단, 작성자 ID, 게시물 URL은 학습 레코드에 넣지 않는다. 출처 감사 기록에는 URL 대신 내부 source ID, 수집일, 이용 근거, 변환 담당자와 원문 폐기 여부만 기록한다. 삭제 요청 대응에 URL이 꼭 필요하면 학습 데이터와 분리된 암호화된 장부에 제한적으로 보관한다.

### 7.3 파일럿 2,000건 구성

첫 SFT는 다음 2,000건이 모두 사람 검수를 통과한 뒤 시작한다.

| 데이터 유형 | 목표 | 비율 | 설명 |
|---|---:|---:|---|
| 동의·라이선스 문맥 | 800 | 40% | A/B등급 자료에서 만든 새 댓글 |
| 공개 블로그 비식별 사실 카드 | 600 | 30% | C등급 글을 원문 폐기 방식으로 변환 |
| 완전 합성 시나리오 | 400 | 20% | 현실적인 가상 글과 이미지 설명 |
| 프로그램 사용자 승인·수정 | 200 | 10% | 앞으로 문맥과 함께 축적되는 피드백 |

출력 유형은 맞춤 댓글 1,200건, 답글 400건, `SKIP` 300건, 나쁜 출력 교정 100건으로 맞춘다. 카테고리는 맛집/카페, 여행, 살림/요리, 육아/일상, IT/제품, 뷰티/패션, 반려동물, 취미/교육의 8개로 나누고 어느 한 카테고리도 전체의 20%를 넘지 않게 한다.

한 블로그나 한 작성자 스타일이 전체의 1%를 넘지 않게 제한하고, 유사 문맥·표현의 근접 중복을 제거한다. 학습/검증/테스트는 행 단위 무작위 분할이 아니라 블로그 source ID와 시나리오 계열 단위로 80/10/10 분할한다.

### 7.4 데이터 제작 및 검수 절차

1. 200~300개의 허용된 참고 글을 8개 카테고리에 고르게 선정한다.
2. 수집 전 `source-policy.jsonl`에 등급, 라이선스/동의 근거, 수집일을 기록한다.
3. 원문을 3~8개의 객관적 사실과 금지 주장으로 변환하고 원문 저장본을 폐기한다.
4. 강한 교사 모델이 서로 다른 관점의 후보 댓글 2~3개와 `SKIP` 판단을 만든다.
5. validator가 허위 경험, 원문 표현 복제, 범용 문구, 최근 댓글 중복, URL, 깨진 문자를 자동 거절한다.
6. 검수 화면에서 사람이 승인·수정·거절하고 이유 코드를 남긴다.
7. 승인본만 `processed/sft-v1.jsonl`로 내보내고 데이터셋 manifest와 SHA-256을 만든다.
8. 테스트 세트 200건은 학습 담당자가 보지 못하도록 고정한다.

검수 이유 코드는 `good`, `generic`, `unsupported_claim`, `copied_phrase`, `duplicate`, `awkward_korean`, `privacy`, `unsafe`, `should_skip`으로 통일한다. 승인자는 사실 카드만 보고 댓글이 그 근거 안에서 작성됐는지 확인한다.

### 7.5 중단 조건과 법적 안전장치

- 사이트 정책이나 권리자가 자동 수집·AI 학습을 허용하지 않으면 해당 소스를 제외한다.
- robots/access 제한을 우회하거나 로그인 세션으로 비공개 범위를 수집하지 않는다.
- 실제 댓글 작성자의 문장을 정답으로 재사용하지 않는다.
- 건강, 금융, 아동, 정확한 주거 위치 등 민감 문맥은 파일럿에서 제외한다.
- 교사 출력이 원문의 연속 8어절 이상 또는 높은 문자 유사도를 재현하면 폐기한다.
- 원문 재현 공격 테스트에서 특정 글의 표현이 복원되면 해당 source 계열을 제거하고 재학습한다.
- 사용 근거가 불명확한 데이터는 수량이 부족하더라도 학습에 넣지 않는다.

### 7.6 데이터 규모

| 단계 | SFT 승인 페어 | 선호 페어 | 목적 |
|---|---:|---:|---|
| 파일럿 | 1,000~2,000 | 0 | 포맷·과적합 확인 |
| 1차 | 5,000~10,000 | 1,000~2,000 | 주요 실패 교정 |
| 확대 | 최대 20,000 | 2,000~5,000 | 부족 구간만 보강 |

수량보다 승인률과 다양성을 우선한다. 단어만 바꾼 유사 문장은 근접 중복으로 제거한다.

### 7.7 SFT 포맷

프로덕션과 같은 채팅 템플릿의 `messages` JSONL을 사용한다.

```json
{"id":"food-001","messages":[{"role":"system","content":"comment-system-v1 전문"},{"role":"user","content":"[제목]\n성수 소금빵 후기\n..."},{"role":"assistant","content":"오전에는 대기가 20분이나 있었군요. 소금빵 단면을 보니 버터 향을 강조하신 이유가 느껴져요 :)"}],"meta":{"category":"맛집","source":"owned_reviewed","prompt_version":"comment-system-v1"}}
```

`SKIP` 정답도 15~20% 포함한다. 항상 댓글을 만들도록만 학습하면 정보 부족·위험 입력에서도 억지 댓글을 만든다.

### 7.8 DPO 포맷

DPO는 SFT 모델의 반복되는 선호 오류가 확인된 뒤에만 쓴다.

```json
{"prompt":[{"role":"system","content":"comment-system-v1 전문"},{"role":"user","content":"구조화된 게시글 입력"}],"chosen":[{"role":"assistant","content":"본문 근거가 있는 자연스러운 댓글"}],"rejected":[{"role":"assistant","content":"좋은 포스팅 잘 보고 갑니다. 제 블로그도 놀러오세요"}],"reason_codes":["generic","self_promotion"]}
```

금지 문구만 rejected로 반복하지 않는다. 난도가 비슷한 후보끼리 비교해야 실제 품질 차이를 배운다. TRL은 SFT와 DPO 훈련기, PEFT 결합을 지원한다.

## 8. 3단계: SFT LoRA/QLoRA

- instruction-tuned 원본 체크포인트에서 시작한다.
- GPU 여유가 있으면 BF16 LoRA, 부족하면 4-bit QLoRA를 사용한다.
- base weight는 고정하고 attention/MLP linear layer에 LoRA를 적용한다.
- assistant 댓글 토큰에만 loss를 주는 설정을 우선한다.
- validation loss와 함께 매 epoch 골든 평가를 실행한다.

초기 탐색 범위:

| 설정 | 파일럿 후보 |
|---|---|
| max sequence length | 512, 768, 1024 |
| LoRA rank | 8, 16, 32 |
| LoRA alpha | rank의 1~2배 |
| dropout | 0.0, 0.05 |
| learning rate | 5e-5, 1e-4, 2e-4 |
| epoch | 1~3, early stopping |
| effective batch | GPU에 맞춰 16~64 |

QLoRA식 `target_modules="all-linear"`도 후보로 두되 실제 Gemma 모듈 이름과 프레임워크 호환성을 확인한다.

파일럿 순서:

1. 100개 데이터 overfit smoke test로 포맷과 loss mask를 확인한다.
2. 1,000~2,000개로 rank/LR 4~6개 조합을 비교한다.
3. 최상위 2개를 3개 seed로 재학습한다.
4. 골든 세트와 블라인드 평가로 프롬프트 기준선과 비교한다.
5. 실패 유형별 데이터만 보강해 1차 모델을 학습한다.

## 9. 4단계: 선택적 DPO

다음 문제가 SFT 후에도 반복될 때만 진행한다.

- 구체적이지만 부자연스러운 후보를 더 선호함
- 본문 근거가 있는 후보보다 과장된 경험담을 선호함
- 최근 댓글과 다른 후보보다 익숙한 매크로 문구를 선호함
- 적절한 `SKIP`보다 무리한 댓글을 선호함

작은 preference 데이터와 여러 beta 후보를 시험한다. 사실성이나 `SKIP` 판단이 악화되면 배포하지 않으며 SFT 단독 모델을 항상 비교군으로 보존한다.

## 10. 평가와 출시 기준

### 자동 평가

기존 `normalizeCommentText`와 `validateBlogComment`를 하네스에서도 그대로 호출한다.

| 지표 | 1차 출시 기준 |
|---|---:|
| 형식 통과율 | 99% 이상 |
| 본문 근거 포함률 | 95% 이상 |
| 명백한 허위 경험 | 1% 이하 |
| URL/홍보/프롬프트 잔재/깨진 문자 | 0% |
| 최근 댓글 유사도 | 기준선보다 악화 없음 |
| 정상 사례의 불필요한 SKIP | 5% 이하 |
| 위험·정보 부족 사례 SKIP 정확도 | 90% 이상 |

골든 세트 확정 후 기준을 한 번 조정하고 이후 출시마다 바꾸지 않는다. 평균뿐 아니라 카테고리와 난도별 최저 성능도 본다.

### 사람 평가

모델명을 숨긴 채 기준선과 후보를 쌍대 비교한다. 본문 맞춤성, 자연스러운 한국어, 사실 근거, 차별성, 예의, 실제 게시 가능성을 1~5점으로 평가한다. 최소 200개 비교에서 기준선 대비 선호 승률 60% 이상이고 치명적 오류가 늘지 않아야 출시한다.

### 운영 평가

- 목표 PC별 TTFT, 생성 시간 p50/p95, tokens/sec
- RAM/VRAM 최대치와 CPU fallback
- 재시도율, validator 거절률, fallback률, SKIP률
- 수정 없이 채택한 비율과 수정 이유
- 실제 페이지의 내 댓글 중복 탐지율
- 제출 문구가 화면에 나타난 비율

실제 게시 실험은 테스트 계정·소량·수동 승인으로 하고 네이버 제한과 정책을 준수한다. 버튼 클릭 성공을 댓글 성공으로 기록하지 않는다.

## 11. GGUF 변환과 앱 배포

1. 선정한 LoRA를 정확한 원본 모델에 병합한다.
2. 공식 토크나이저와 채팅 템플릿을 보존해 llama.cpp 호환 GGUF로 변환한다.
3. 현재 호환 기준 Q4_0과 품질 후보 Q4_K_M을 같은 하네스로 비교한다.
4. 파일 크기, SHA-256, 원본 revision, 양자화 도구 commit을 manifest에 기록한다.
5. `llama-server`의 `/v1/chat/completions`로 단독 smoke test를 한다.
6. `apps/engagement`에 canary 모델로 등록하고 기존 모델을 유지한다.
7. `windows` 카탈로그와 검증 로직의 일치를 자동 테스트한다.

GGUF에 임의 암호화 헤더를 붙이면 표준 로더와 호환되지 않는다. 보호가 필요하면 배포 권한을 확인한 뒤 설치 파일 접근 통제, 서명, 해시 검증을 별도로 설계한다.

## 12. 배포와 롤백

| 단계 | 범위 | 통과 조건 |
|---|---|---|
| Offline | 골든 세트 | 자동·사람 평가 충족 |
| Shadow | 생성하되 게시 안 함 | 지연·거절률 정상 |
| Canary | 테스트 계정, 소량 수동 승인 | 허위/중복/깨진 출력 없음 |
| Opt-in | 일부 사용자 선택 | 기준 모델보다 수정률 감소 |
| Default | 기본 모델 전환 | 7일 이상 회귀 없음 |

앱 설정에 `model_id`, `model_hash`, `prompt_version`, `validator_version`을 함께 기록한다. 치명적 출력, validator 실패 증가, 지연 급증 시 기존 모델과 프롬프트로 한 번에 롤백한다.
